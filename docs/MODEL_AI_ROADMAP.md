# 예측 모델 고도화 및 AI 활용 로드맵

작성 기준일: 2026-08-22

## 결론

현재 `KBO_MATCHUP_V9`, `MLB_MATCHUP_V8`은 선수·팀 지표를 보수적 계수로 결합하고 과산포 Monte Carlo로 경기 결과를 생성하는 **투명한 후보 모델**입니다. 아직 과거 데이터에서 학습해 최적화된 머신러닝 모델은 아닙니다.

정확도를 가장 크게 높이는 순서는 다음과 같습니다.

1. 경기 당시 실제로 알 수 있었던 데이터 스냅샷을 충분히 축적합니다.
2. 단순하지만 학습 가능한 통계 베이스라인을 만듭니다.
3. 같은 경기·같은 시점에서 기존 모델과 새 모델을 비교합니다.
4. 타석 단위 결과와 주자·아웃 상태를 반영하는 시뮬레이터로 발전시킵니다.
5. LLM은 점수를 임의로 예측시키지 않고 뉴스·부상·라인업의 구조화와 설명에 사용합니다.

지표 개수가 많아지는 것 자체는 정확도 향상을 보장하지 않습니다. `표본 외 날짜순 성능이 실제로 좋아진 지표만` 남겨야 합니다.

## 1. 가장 먼저 필요한 데이터 기반

### 불변 경기 전 스냅샷

각 경기마다 최소 `T-24h`, `T-3h`, `T-60m`, `T-15m`의 원본과 특징값을 수정 불가능한 스냅샷으로 보존합니다.

- 수집 시각과 원천의 업데이트 시각
- 선발 확정 여부·변경 이력
- 예상/확정 라인업과 타순
- 당시까지의 시즌·최근 5/10/20경기 기록
- 투수 휴식일, 최근 투구 수·소화 이닝
- 불펜의 최근 1/3/7일 투구 수와 연투 여부
- 구장, 날씨, 바람, 온도, 우천·돔 여부
- 타자/투수 좌우 유형과 상대전적 표본 수
- 시장 기준점은 비교용 별도 스냅샷
- 결측값, 대체값, 데이터 출처, 모델 버전
- 경기 종료 후 최종 점수와 이닝별 실제 득점

가장 중요한 누수 방지 규칙은 `feature.available_at <= prediction.created_at <= game.start_at`입니다. 시즌 최종 성적이나 경기 후 수정된 기록을 과거 경기에 채워 넣으면 높은 백테스트 성적이 나와도 실제 운영에서는 재현되지 않습니다.

### 데이터 품질 지표

- 시점별 스냅샷 완성률
- 선발·라인업 ID 매칭률
- 선수 중복·이름 충돌률
- 수집 지연의 중앙값·95백분위
- 각 특징의 결측률과 비정상값 비율
- 경기 전 예측 없이 종료된 경기 수

모델 개발보다 먼저 이 지표를 대시보드로 만드는 것이 좋습니다. 정확한 모델도 잘못된 선발 ID 하나에 크게 흔들릴 수 있습니다.

## 2. 학습형 통계 베이스라인

현재 규칙 모델의 다음 비교 대상으로 아래 세 모델을 같은 데이터에 학습합니다.

### 승패: 정규화 로지스틱 회귀

- 목적값: 홈 승리 1, 원정 승리 0
- 장점: 작은 데이터에서도 안정적이고 계수 방향을 설명하기 쉽습니다.
- 역할: 복잡한 모델이 실제로 의미 있는 개선인지 판별하는 기준입니다.

### 득점: Poisson과 Negative Binomial 비교

- 홈·원정 득점을 별도 모델로 추정합니다.
- 평균과 분산이 비슷하면 Poisson, 득점 분산이 더 크면 Negative Binomial이 유리할 수 있습니다.
- 경기 환경에 따른 양 팀 득점 상관은 공유 랜덤 효과 또는 시뮬레이션 단계에서 반영합니다.
- 야구 득점과 팀 효과에 다층 모형을 적용하는 접근은 [Jim Albert의 야구 득점 연구](https://journals.sagepub.com/doi/10.3233/JSA-140001)와 같은 방향입니다.

### 계층적 축소 모델

상대투수 통산 타율 5타수 3안타는 60%라는 숫자보다 `표본이 5타석뿐`이라는 사실이 더 중요합니다.

- BvP, 투수의 상대팀 기록, 팀 간 상성을 리그 평균 쪽으로 축소합니다.
- 선수 → 팀 → 리그의 계층 구조로 데이터가 적은 신인·교체 선수도 과대평가하지 않습니다.
- 시즌 초에는 전년도·최근 2~3년 기록을 나이·리그 변화에 맞춰 감쇠해 사전분포로 씁니다.
- 상대전적은 최소 표본 기준으로 버리지 말고, 표본에 따라 영향이 연속적으로 커지게 합니다.

## 3. 머신러닝 후보 모델

스냅샷과 결과가 충분히 쌓이면 LightGBM·XGBoost·CatBoost 같은 트리 기반 부스팅을 후보로 추가합니다. 첫 도입부터 딥러닝을 쓸 필요는 없습니다.

### 권장 특징 그룹

| 그룹 | 예시 |
|---|---|
| 팀 공격 | wOBA/OPS/OBP/SLG, 좌우 split, 최근 가중 성적, 주루 |
| 선발 | ERA·FIP·xFIP·WHIP, K/BB, GB%, 구종 비율, 예상 이닝 |
| 타선-선발 | BvP 축소값, 좌우 상성, 구종별 성적, 타순별 생산력 |
| 불펜 | 가용 투수, 최근 투구 수, 연투, 역할별 성적 |
| 수비·포수 | 수비 지표, 포수 프레이밍·도루 억제(라이선스 가능 시) |
| 환경 | 구장 팩터, 온도·습도·바람, 돔, 심판 성향(가능 시) |
| 일정 | 이동 거리, 휴식일, 더블헤더, 전날 연장전 |
| 데이터 상태 | 선발·라인업 확정, 결측 플래그, 수집 시점 |

MLB는 허가된 범위에서 [Baseball Savant Statcast Search](https://baseballsavant.mlb.com/statcast_search)의 타구 속도·발사각·배럴·기대 타율/장타율/wOBA, 구속·회전·무브먼트 같은 정보를 후보로 검토할 수 있습니다. 기술적으로 조회 가능하다는 것과 상업적 이용·재배포 권리는 별개이므로 유료화 전 라이선스를 확인합니다.

### 학습·검증 방식

- 무작위 K-fold 대신 날짜순 expanding-window walk-forward를 사용합니다.
- 하이퍼파라미터 조정 기간과 최종 테스트 기간을 분리합니다.
- 동일 경기·동일 시점 예측끼리만 비교합니다.
- 모델, 특징 스키마, 학습 구간, 코드 커밋, 데이터 해시를 함께 버전 관리합니다.
- 새 모델은 바로 교체하지 않고 shadow 예측을 저장하는 challenger로 운영합니다.
- SHAP 또는 permutation importance로 결과 근거를 만들되, 설명값을 인과관계로 표현하지 않습니다.

## 4. 타석 단위 시뮬레이터

현재처럼 경기 총 기대득점을 9이닝에 배분하는 방식보다 의미 있는 다음 단계는 각 타석을 진행시키는 것입니다.

### 타석 결과 분포

각 타석에서 다음 결과의 확률을 추정합니다.

`BB, HBP, K, 1B, 2B, 3B, HR, 기타 아웃`

입력에는 타자·투수의 장기 실력, 좌우 유형, 상대투수 기록의 축소값, 구종 조합, 선발 피로, 타순, 구장·날씨를 사용합니다. 단순 타율보다 OBP·SLG·wOBA와 삼진·볼넷·장타 유형을 나누는 것이 득점 과정에 더 적합합니다.

### 경기 상태 진행

- 8개 주자 상태 × 3개 아웃의 24개 base-out 상태
- 실제 타순 순환과 대타·교체 가능성
- 선발의 예상 투구 수·타순 세 번째 상대 효과와 교체 확률
- 불펜 가용성과 역할별 투수 선택
- 홈팀 리드 시 9회말 생략
- 동점 시 연장 규칙
- 우천·더블헤더 등 리그 규칙 분기

20,000회 시뮬레이션의 각 시행에서 이 과정을 반복해 승률, 정수 대표 스코어, 이닝별 분포, 총점 구간을 계산합니다. UI에는 단 하나의 이닝 흐름만 확정값처럼 표시하지 말고, 대표 흐름과 함께 이닝별 득점 확률 또는 신뢰 구간을 보여주는 것이 정직합니다.

## 5. 앙상블과 확률 보정

서로 다른 오류를 내는 모델을 결합합니다.

- 통계 GLM: 안정성과 해석력
- 트리 부스팅: 비선형 상호작용
- 타석 시뮬레이터: 야구 진행 구조
- 현 V7/V6: 기존 비교 기준

앙상블 가중치는 감으로 정하지 않고 이전 기간의 표본 외 성능으로 학습합니다. 승률은 sigmoid/Platt, isotonic 또는 temperature scaling 후보를 날짜순 별도 보정 구간에서 평가합니다. [scikit-learn 확률 보정 문서](https://scikit-learn.org/stable/modules/calibration.html)가 설명하듯, 80%라고 낸 경기들이 장기적으로 약 80% 승리해야 해석 가능한 확률입니다. Brier Score만으로 calibration을 단독 판단하지 않고 reliability diagram과 ECE를 함께 봅니다.

## 6. 평가 기준과 모델 승격 규칙

### 필수 지표

| 대상 | 지표 | 해석 |
|---|---|---|
| 팀별 득점 | MAE, RMSE | 낮을수록 좋음 |
| 총점 분포 | 구간 포함률, CRPS 또는 pinball loss | 불확실성까지 평가 |
| 승률 | Brier Score, Log Loss | 낮을수록 좋음 |
| 확률 신뢰성 | reliability diagram, ECE | 예측 확률과 실제 빈도 비교 |
| 순위 판별 | AUC(보조) | 확률 자체의 품질을 대신하지 않음 |

### 비교 대상

- 현 `KBO_MATCHUP_V9`, `MLB_MATCHUP_V8`
- 날짜 이전 홈팀 승률만 쓴 단순 기준
- 리그 평균 득점 Poisson
- 같은 경기 시점의 마진 제거 시장 컨센서스

시장 값은 독립적인 비교 기준으로 유지하고 모델 입력으로 쓰지 않습니다. 시장을 입력에 넣으면 시장보다 나은 자체 신호가 있는지 판별하기 어렵습니다.

### 권장 표본과 승격 문턱

- 200경기: 예비 점검. 결론보다 버그·누수·큰 편향을 찾는 단계
- 500경기: 첫 후보 비교의 권장 최소값
- 학습형 정식 모델: 가능하면 여러 시즌의 수천 경기로 학습하고 최신 시즌을 최종 테스트로 분리
- 리그와 예측 시점별(`T-24h`, `T-3h`, `T-60m`, `T-15m`) 성능을 따로 확인
- 같은 경기의 손실 차이를 paired bootstrap으로 계산해 95% 구간을 제시

새 후보는 다음 조건을 모두 만족할 때만 champion으로 승격합니다.

1. 같은 경기에서 승률 Brier Score 또는 Log Loss가 실질적으로 개선됩니다.
2. 팀 득점 MAE가 악화되지 않고, 목표가 득점 모델이면 유의미하게 개선됩니다.
3. calibration이 악화되지 않습니다.
4. 특정 한 달·한 리그·한 팀에만 개선이 몰리지 않습니다.
5. 핵심 특징 그룹을 제거한 ablation에서 개선 원인이 재현됩니다.
6. 운영 중 결측·수집 지연 상황에서도 안전한 대체값과 이전 모델 fallback이 동작합니다.

## 7. AI/LLM을 잘 활용하는 방법

### 현재 구현된 제한형 앙상블

`KBO_MATCHUP_V9`/`MLB_MATCHUP_V8`은 명시적으로 활성화된 경우 Claude에 팀명, 리그·구장, 파생 통계 특징, 통계 베이스라인만 보내 구조화된 보조 예측을 받습니다. Claude의 승률은 베이스라인 대비 ±12%p, 팀별 기대득점은 ±1.2점 범위로 먼저 제한하며, 자신도 반영 후 최대 25% 이하로 앙상블합니다. 외부 호출 실패 시 통계 모델로 복귀하고 실패 유형만 저장합니다. 이 후보가 실제로 정확도를 높인다는 전제는 두지 않으며, Claude 사용/미사용 스냅샷을 같은 경기·같은 시점의 walk-forward 성능으로 비교해야 합니다.

### 효과적인 사용처

#### 뉴스·부상·라인업 구조화

라이선스가 허용된 기사·보도자료에서 다음 형태의 엄격한 JSON을 추출합니다.

```json
{
  "league": "KBO",
  "team_id": "...",
  "player_id": "...",
  "event_type": "INJURY|REST|LINEUP_CHANGE|ROLE_CHANGE",
  "status": "CONFIRMED|EXPECTED|RUMOR",
  "effective_at": "2026-08-22T18:00:00+09:00",
  "source_url": "...",
  "published_at": "...",
  "confidence": 0.0
}
```

LLM 출력은 JSON Schema 검증, 선수 ID 매칭, 원문 URL·발행 시각 보존, 중복 제거를 통과해야 합니다. `RUMOR`는 기본 모델에 넣지 않고 UI 참고 정보로만 표시합니다.

#### 엔터티 매칭과 데이터 QA

- 한글/영문/약칭이 다른 동일 선수·팀 후보 찾기
- 갑자기 ERA가 0 또는 99가 된 비정상 데이터 설명
- 스케줄·선발·라인업 소스 사이의 충돌 요약
- 수집 오류 로그 묶음의 원인 후보와 재현 절차 작성

AI가 자동 수정하기보다 후보를 제시하고, 규칙 검증이나 관리자 승인을 거쳐 반영합니다.

#### 근거 기반 경기 설명

모델이 계산한 실제 특징 차이와 기여도를 입력으로 주고 자연어 설명만 생성합니다. 모든 문장은 근거 특징 ID와 연결하며, 모델에 없는 부상·감정·기세를 임의로 추가하지 못하게 합니다.

#### 사용자 질의 도우미

저장된 데이터만 검색해 `왜 3시간 전보다 두산 승률이 내려갔나?` 같은 질문에 선발·라인업·시장 스냅샷 변화로 답하게 할 수 있습니다. 응답에는 시점과 출처를 표시합니다.

### 모델 입력으로 쓸 수 있는 비정형 신호

부상·휴식·역할 변경처럼 객관적으로 구조화 가능한 사건만 작은 가중치의 후보 특징으로 만듭니다.

`허가된 원천 → 변경 문서 수집 → LLM JSON 추출 → 스키마/ID/시각 검증 → 사람 또는 규칙 승인 → feature store → 기존 수치 모델`

각 신호는 빼고 넣는 ablation을 통해 walk-forward 성능이 실제로 개선될 때만 유지합니다. 기사 감성 점수나 SNS 분위기는 교란이 크므로 후순위입니다.

### 사용하지 말아야 할 방식

- 통계 입력 없이 LLM에 `오늘 누가 이겨?`라고 물어 확률 생성
- 없는 부상·상대전적·라인업을 추정하도록 허용
- 경기 후 기사나 최종 시즌 기록을 경기 전 특징에 섞기
- 출처·시각 없는 뉴스 요약을 자동 게시
- LLM 설명을 모델의 실제 계산 근거인 것처럼 표시
- 검증 없이 감성·화제성을 큰 가중치로 반영

LLM은 숫자 예측기의 대체물이 아니라 **비정형 정보를 안전하게 정형화하고 결과를 설명하는 보조 계층**입니다.

## 8. 비용을 고려한 구현 순서

### 1단계: 현재 서버에서 가능

1. 스냅샷 완성도·결측률 대시보드
2. 학습 데이터셋 생성 CLI와 feature registry
3. 로지스틱·Poisson·Negative Binomial 베이스라인
4. 모델 registry와 champion/challenger shadow 저장
5. walk-forward·calibration·ablation 리포트

이 단계는 게임 단위 표 데이터이므로 Oracle VM 또는 로컬 CPU로 충분합니다.

### 2단계: 데이터 권리 확인 후

6. MLB Statcast 고급 특징 및 KBO 상용 고급 피드 연결
7. 타석 단위 base-out 시뮬레이터
8. 불펜 가용성·날씨·심판·이동 정보

비용의 핵심은 GPU보다 데이터 라이선스와 저장·정제입니다.

### 3단계: 효과가 검증될 때만

9. 허가된 뉴스의 LLM 구조화 파이프라인
10. 변경된 문서만 content hash로 처리하고 결과 캐시
11. 작은 모델과 엄격한 schema부터 사용하고 비용·오류율 모니터링
12. 투구 단위 딥러닝·시계열 모델은 데이터량과 기존 부스팅 대비 개선이 확인될 때만 실험

## 바로 다음 개발 작업

1. DB에서 모든 경기 전 입력을 학습용 한 행으로 내보내는 `dataset build` 명령을 추가합니다.
2. 특징별 `available_at`, 출처, 결측·대체 여부를 저장합니다.
3. 로지스틱·Poisson·Negative Binomial 모델을 학습하고 파일·메타데이터를 버전 관리합니다.
4. 한 번의 갱신에서 V7/V6와 새 후보 모두를 저장하는 shadow prediction을 구현합니다.
5. 백테스트에 모델별 calibration plot, 특징 ablation, paired bootstrap 승격 판정을 추가합니다.
6. 데이터가 쌓이는 동안 타석 결과·24 base-out 상태 시뮬레이터를 별도 실험 플래그로 개발합니다.
7. LLM 기능은 라이선스된 기사 소스가 정해진 뒤 `AI_NEWS_FEATURES=false` 기본값으로 연결합니다.

이 순서를 따르면 복잡해 보이는 AI가 아니라, 실제 표본 외 성능으로 검증된 모델만 서비스에 남게 됩니다.
